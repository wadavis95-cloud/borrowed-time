Control response measurements

Control response timings currently cover online races. Gesture entry includes time spent recognizing a swipe; recognized-input timing starts once an action is known. A processed acknowledgment means the server handled the command, not that the action was accepted. Anticipated lane timing ends when the first corresponding provisional lane pose is submitted before snapshot confirmation; it does not establish acceptance. Confirmed render timing ends when the matching confirmed state is submitted to the renderer. Renderer submission is not input-to-photon latency: GPU work and screen presentation are not measured.

Displayed movement age follows the local runner’s submitted world timeline relative to the latest snapshot receipt; it is not absolute server-state age. Opponent buffering is measured separately. Projection reports bounded forward extrapolation beyond received authority. Only local lane switches anticipate inputs; jumps and paid abilities still require server confirmation. Lane corrections and expired intentions show when provisional movement had to settle against authority or timed out. Missing matches and missing samples do not mean zero delay.

Update delivery timing

Server schedule delay measures late application sends. Excess arrival compares consecutive send and receive intervals without synchronizing clocks; it is not one-way latency and includes browser scheduling. Measurements cover the same process lifetime.

Brief spikes and movement buffering

p99 shows rarer delays. Recorded maxima cover instrumented reports only; old reports may lack peaks. The buffer target applies to opponents. Own-player lane anticipation is measured separately; neither value is end-to-end screen latency.

Recent report peaks and server pauses

One peak per metric per report, up to 24 report peaks and 24 server samples. Client times are approximate, rounded to 100 ms; device clocks may differ. Server pauses are measured independently. These lists do not establish causation.

    How to read this dashboard
    • Capacity includes online racers and lobby guests. The showcase demo runs on the viewing device and uses no race connections or server lobby.
    • CPU, memory and event-loop delays come from this server. They do not measure phone graphics performance.
    • Network RTT is a lightweight application echo. Processed acknowledgment measures command send through a snapshot acknowledging processing, not action acceptance or display. Snapshot gaps target about 50 ms.
    • HTTP bytes count declared completed response bodies, not partial aborted downloads or transport headers. Race bytes count JSON queued to sockets. Neither is a hosting invoice.
    • Hourly bandwidth projects the latest 30-second average; it is a scenario estimate, not a forecast. Game rates exclude monitoring; a separate card includes dashboard/API response bodies. The hourly projection includes that monitoring output.
    • History lasts up to 30 minutes. The latest minute retains one-second samples; older chart buckets show peak CPU/memory/delay and average rates over roughly ten seconds. Totals reset on restart; client observations expire after 30 minutes or earlier at the 6,000-report cap. No external alerts or durable storage yet. Detecting an outage while this dashboard is closed requires an external health monitor.
    • Signals use provisional sustained thresholds. Calibrate them on the target host before treating them as service guarantees.
    • Browser reporting is capped at 600 reports/minute globally. Payloads stay below 2,048 bytes and may be split; a report is not a unique player or session. The browser retains at most four outgoing payloads including its active request, discards excess or failed payloads, and reports those losses on a later normal flush without retries. Rejected or discarded reports mean coverage is incomplete. Phase attribution is retained across asynchronous sends; clients without phase data appear as unknown. Long tasks are unavailable in some browsers.
